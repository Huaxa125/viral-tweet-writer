# Thread 结构

只有在需要展开完整论证、故事或教程时才使用 Thread。不要因为原文很长就自动生成 Thread。

## 核心规则

- 让第 1 条拥有明确承诺或矛盾，能够独立吸引读者。
- 让每一条承担不同作用，并成为可以独立进入的阅读入口。
- 确保读者从 Thread 中间看到某一条时仍能理解。
- 持续推进内容，不要把一个长段落机械切成编号碎片。
- 使用经过验证的真实细节，保留作者实际经历的先后顺序。
- 用总结或适度的下一步行动结束。

## 1. 拆解型 Thread

适合作者为某件事投入了明显时间或成本，并总结出多条经验时使用。

```text
第 1 条：钩子——投入了多少时间或成本、做了什么、结果如何
第 2 条：承诺——将分享多少条、什么类型的经验
第 3 至 N 条：每条一个经验，加一至两句解释
倒数第 2 条：最反直觉的经验
最后 1 条：总结，并在有必要时加入相关 CTA
```

不要为了凑数量加入空洞经验。每一条都必须提供独立价值。

## 2. 故事型 Thread

适合包含矛盾、转折和有用结论的真实经历。

```text
第 1 条：故事起点，制造有依据的悬念
第 2 至 5 条：每条推进一个真实转折
第 6 条：高潮、结果或决定性认知
第 7 至 8 条：从故事中提炼可迁移的经验
最后 1 条：总结，并在有必要时加入相关 CTA
```

认知是讲故事的原因。禁止编造事件，也不要为了薄弱结果拖延揭晓。

## 3. 教程型 Thread

适合读者看完后可以完成一项具体任务的内容。

```text
第 1 条：读者痛点、要完成的任务和现实可达的结果
第 2 条：前提条件
第 3 至 N 条：每条一个可执行步骤
倒数第 2 条：作者验证过或亲身踩过的常见坑
最后 1 条：总结，并在确实有用时加入收藏提示或 CTA
```

只有截图、示例或代码真实存在或可以生成时，才承诺提供这些材料。

## 独立入口检查

读者可能通过回复、引用、截图或算法推荐看到 Thread 中的任何一条。逐条检查：

- 脱离上一条后，当前内容的主语和主题是否仍然明确？
- 当前内容是否提供完整的微型价值？
- 当前内容是否仍然让读者有理由查看完整 Thread？

必要时补充最少量上下文，但不要在每一条中重复完整前提。
